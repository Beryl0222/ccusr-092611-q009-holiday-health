# 假期健康提醒编排说明

假期健康提醒编排需要在多方参与、事件顺序不稳定和服务重启的情况下保持记录一致。

## 记录与一致性

- 每条业务记录有所属方（计划负责人/授权人）、状态与递增版本，乐观版本冲突
  返回 `ConflictError`。
- 所有状态变化写入只增的 `events` 事件表（创建、授权授予/撤销、风险变更、
  措施生成/作废/完成、提醒投递、症状上报、升级开立/确认/结案）。
- 写操作以调用方 `request_key` 幂等：键内缓存响应，重复提交与重复同步不会
  二次触发；已完成措施是终态，任何后续同步都不会使其复活或产生新修订。

## 风险增量重算

风险按“目的地 + 日期区间 + 等级”窗口登记，版本在同一目的地内单调递增
（等级不变不升版）。每个措施模板按自身窗口覆盖日期生成风险版本摘要：

- 摘要不变（包括重复同步）→ 完全不动；
- 摘要变化 → 旧修订置 `superseded` 并写入新修订，未完成待办的语义延续；
- 模板因风险下调消失 → 未完成条目作废，已完成历史保留；
- 洗手、日常监测、成人建议与风险无关，不参与重算。

## 时间口径

- 存储统一为带时区 UTC；计划日期是目的地当地日期，按 IANA 时区锚定当天
  00:00 后换算 UTC（如东京 7/1 00:00 = UTC 6/30 15:00）。
- 回程后监测窗口为回程日起一个自然月：第 1–14 天为早段、第 15 天至满月前
  一天为晚段；满月当天及以后上报的症状不属于本计划监测窗口。
- 当前时间通过可注入的 `Clock`（`SystemClock`/`FixedClock`）获取，提醒生成、
  症状窗口判定均由时钟驱动，便于确定性测试。

## 年龄分流

成员在出发当日是否满 18 岁决定儿童/成人角色。儿童的“暂缓集体活动”与
成人的“回程健康建议”使用不同 kind 与 audience 分别建条、分别完成、分别留痕。

## 权限、取消与重启

- 授权必须由计划负责人授予且仅本人可撤销；撤销后该成员的未完成措施作废，
  后续同步跳过，重新授权后可再生成。
- 计划仅负责人可取消；取消作废全部未完成措施，但保留事件与已完成历史。
- 症状升级是临床安全对象：计划取消或授权撤销都不影响已开立的升级，值班人员
  仍可确认与结案。
- 服务无内存业务状态：重新打开同一 SQLite 文件即完成“重启”，`duty_handoff`
  返回待处理升级与未完成待办（就医相关成员置顶），历史事件可逐条解释。

## 就医优先

疫区返回者（行程内窗口为 moderate/high；回程后继承行程末日暴露）出现
发热、腹泻、呕吐、皮疹、黄疸、咳嗽、呼吸困难等预警症状时，系统立即开立
`urgent_care` 升级，返回分步就医路径（隔离、报告、指定发热门诊、检测、
聚集限制），并将该成员的待办提醒排到所有普通提示之前。
